# Resolve and validate aliases offline against a bundled snapshot

## Context and Problem Statement

Authors write short field names such as `publicNetworkAccess`. Azure Policy needs full aliases such as `Microsoft.Storage/storageAccounts/publicNetworkAccess`. A misspelled alias is not rejected when the policy is created. It just never matches, so the policy is silently ineffective. How does Bylaw resolve and validate alias names without depending on Azure while compiling?

## Decision Drivers

* Compiling must work offline and in CI without credentials (ADR-0007).
* Unknown or misspelled aliases must fail the build.
* The full alias set is large, so loading it must not make every build slow.
* The installed module folder may be read-only, and it is replaced on every module update.

## Considered Options

* A bundled snapshot plus an optional refreshed cache, with lookup-based resolution
* A live lookup through Az at compile time
* No validation: concatenate `<type>/<name>`

## Decision Outcome

Chosen option: "A bundled snapshot plus an optional refreshed cache, with lookup-based resolution".

### Snapshot format

```json
{
  "schemaVersion": 1,
  "generatedAt": "2026-11-25T00:00:00Z",
  "types": {
    "Microsoft.Storage/storageAccounts": {
      "aliases": {
        "Microsoft.Storage/storageAccounts/publicNetworkAccess": { "modifiable": true },
        "Microsoft.Storage/storageAccounts/networkAcls.ipRules[*]": {},
        "Microsoft.Storage/storageAccounts/networkAcls.ipRules[*].value": {}
      }
    }
  }
}
```

* Whether an alias is an array is derived from `[*]` in its name. Only facts that can't be derived are stored (`modifiable`, which `Modify` needs in Milestone 2).
* The snapshot is written with the canonical writer (ADR-0009), with types and aliases sorted by ordinal comparison, so refreshing it gives minimal diffs.
* The loader parses the file once per runspace, and indexes only the resource types the build references.

### Where the snapshot is loaded from (first match wins)

1. `Build-Bylaw -AliasCachePath`
2. `aliasCache` in `bylaw.json` (ADR-0012), relative to that file
3. The user cache, at `$HOME/.bylaw/aliases.json`
4. The bundled `src/Data/aliases.json`, which is read-only and ships with the module

`Update-BylawAliasCache` calls `Get-AzPolicyAlias`, which needs a signed-in Az context. It writes to the user cache by default, or to `-OutputPath`. It never writes into the module folder. The full bundled snapshot is generated by the maintainers using the same command.

### Resolution rules, in order

1. **Reserved fields** pass through unchanged and are not aliases: `name`, `fullName`, `kind`, `type`, `location`, `id`, `identity.type`, `identity.userAssignedIdentities`, `extendedLocation`, `extendedLocation.name`, `extendedLocation.type`, `tags`, `tags['<name>']` and `tags.<name>`.
2. **Full alias** (the name contains `/`): checked against the snapshot. The casing from the snapshot is emitted.
3. **Short name under `Resource '<type>'`**: an exact match on `<type>/<name>`, ignoring case. Otherwise, a unique match among that type's aliases whose name ends in `/<name>`. Not every alias is prefixed with its full type path, for example `Microsoft.Compute/imagePublisher` under `Microsoft.Compute/virtualMachines`, so this is a lookup, not string concatenation. More than one match is an error that lists the candidates.
4. **Inside `Each <array>[*]`**: `Field x` resolves to `<array alias>[*].x`, and `Item` refers to the element itself (`<array alias>[*]`), for arrays of plain values.
5. **`Resource *`**: there is no type context, so only reserved fields and full aliases are allowed.
6. **`[*]` outside `Each`** is a compile error. Azure evaluates a `[*]` field condition as "every element satisfies it", and as true for an empty array, so negating it by swapping the operator would be wrong. See ADR-0002.

### Unknown aliases

* An unknown alias is a compile error. The message includes the closest matches from the snapshot.
* `Field x -AllowUnknownAlias` allows it for one field. A short name is then built as `<type>/<name>`.
* `Build-Bylaw -AllowUnknownAlias` allows it for the whole build. Each use is still reported as a warning.

### Consequences

* Good, because compiling is offline and deterministic, and typos fail the build.
* Good, because a refreshed cache never needs write access to the module folder.
* Bad, because the bundled snapshot goes stale between releases. Users who need new aliases run `Update-BylawAliasCache`.

### Confirmation

Unit tests cover each resolution rule, each error, the order in which snapshot locations are tried, and stable output from a refresh (with Az mocked).
